## What This Is

A personal AI-powered life assistant and calendar, built as a multi-page HTML prototype. No framework build step — each page is a self-contained React 18 + Babel file served by a local Python server. The server also proxies Claude API calls to avoid CORS.

**The app's one user is Benny B, and he starts with a completely blank schedule** (see session 5). There is no seeded sample data anywhere — every hardcoded `EVENTS`/`TASKS`/`EVENTS_BY_DATE` array across all four pages is empty. The only events that exist are whatever the assistant (`bot.html`) has written to `localStorage['cal_bot_events']`, plus whatever's in `cal_action_bot_tasks`. "Today" is computed from the real device clock everywhere (`todayKey()`, defined per-file) — there is no more fixed fictional "today" date. This matters: it's what makes a bot-scheduled plan actually show up when you open the calendar, instead of landing on a date the app doesn't think is "now" (see the session 5 bug writeup below).

**To start the app:**
```bash
cd ~/Desktop/calendar-prototype
python3 server.py
```
Then open: **http://localhost:5173**

## How to Run

Python 3.9+ only, no pip installs required. Uses only stdlib (`http.server`, `urllib.request`).

```bash
python3 server.py
```

The server:
- Serves all `.html` files as static files at `http://localhost:5173/`
- Exposes `POST /api/chat` which reads `ANTHROPIC_API_KEY` from `.env` and proxies to `https://api.anthropic.com/v1/messages`
- Logs all requests to the terminal

If the API key is missing or the call fails, `bot.html` falls back to keyword-matched demo responses automatically.

## Design System

**As of July 28 2026 the whole app runs on CSS custom properties, not hardcoded hex/rgba.** The old lavender palette (`#3b3557`, `#a78bfa`, `#818cf8`, `rgba(167,139,250,...)`, etc.) is gone from every file — a `grep` for those strings across `*.html` should return nothing. Apply the token system below to any new page; never hardcode a color.

### Category colors — derived, not hand-authored
Each event type has exactly one token (`--cat-work`, etc.) — bg tint / border / text / tag-pill / swatch are all *derived from it at render time* via CSS `color-mix()`, so both themes stay in sync automatically with zero JS branching:

```javascript
function catStyle(name) {
  const v = 'var(--cat-' + name + ')';
  return {
    bg: 'color-mix(in srgb, ' + v + ' 20%, var(--surface))',
    bd: 'color-mix(in srgb, ' + v + ' 55%, transparent)',
    tx: 'color-mix(in srgb, ' + v + ' 68%, var(--text-primary))',
    tg: 'color-mix(in srgb, ' + v + ' 30%, transparent)',
    sw: v,
  };
}
const C = { work: catStyle('work'), personal: catStyle('personal'), /* ...social, travel, free, health */ };
```
(`calendar.html`/`bot.html` use a `dot` key instead of `sw`/`tg` — same `catStyle` idea, fewer fields, since those pages only need a swatch dot.) This relies on `color-mix()` support (confirmed working in the preview browser — modern Chromium only, no fallback authored).

### Typography / Cards / Nav
Same structure as before, just token-based now:
- Page title 27px/700, `color: var(--text-primary)`; gradient span uses `linear-gradient(130deg, var(--accent-primary), var(--accent-hover))`.
- Subtitle 14px, `var(--text-secondary)`; small labels `var(--text-muted)`.
- Cards: `background: var(--surface-elevated)`, `border: 1px solid var(--border)`, `backdrop-filter: blur(14px)`.
- Nav active pill: `color-mix(in srgb, var(--accent-primary) 18%, transparent)` bg, `var(--accent-hover)` text.
- Box-shadow colors were **left as literal purple-ish rgba in a few low-visibility spots** (e.g. `Bubble` hover shadow in `index.html`) — a known, deliberately-scoped gap, not a bug. Everything else (surfaces, text, borders, category colors, gradients) is tokenized.

### Settings gear
A small `SettingsGear` component (⚙ in a circular `var(--surface-elevated)` button, links to `settings.html`) is duplicated top-right of the header row on all 4 non-settings pages, same duplication pattern as `Nav`. The gear glyph is wrapped in its own `<span style={{transform: 'translateY(-2px)'}}>` (session 6) — the `⚙` character renders visibly low within its own line box in this font (confirmed via `getBoundingClientRect`: the flex-centered container box was already mathematically exact, the glyph itself just isn't centered within its own metrics), so a small manual nudge on the inner span corrects it without moving the button itself. If the icon or font ever changes, re-check this offset visually.

## Pages

### index.html — Today (Daily Schedule)

**URL:** `http://localhost:5173/index.html` or `http://localhost:5173/index.html?date=YYYY-MM-DD`

**Purpose:** Vertical timeline of the day from 7am–9pm. Launched from the "Today" nav tab or by clicking a day in the calendar.

**Key components:**
- `Grid` — hour labels (7am–9pm) + 1px horizontal grid lines. `PX_HR=80` pixels per hour.
- `NowLine` — pink→purple gradient line at current time. Updates every 30s. No timestamp label (was removed by user request).
- `Bubble` — event card. Three size tiers based on height: XS (<40px, row layout), SM (<64px, with subtitle), full (with subtitle + tag + time range). **Clickable** — navigates to `action.html?event=<id>&date=<SELECTED_KEY>` to see that event's checklist (session 5; previously opened an in-page `DetailModal`, now removed — see action.html's `FocusedEvent`). Also carries a small **✎ edit pencil** next to the time label (session 9, opacity-faded until the card is hovered), `stopPropagation`'d so it opens `EventModal` instead of navigating to action.html.
- `Pills` — summary row at bottom, computed live from today's real events (meeting/free/travel/health counts) — session 5 replaced the old mostly-hardcoded strings ("5 meetings", "Gym at 4 pm") with real numbers, and the whole row now renders nothing when there's nothing scheduled.
- `Nav` — shared nav bar, active: `'today'`.
- `AddEventButton` / `EventModal` (session 9) — same shared create/edit modal as calendar.html's copy (identical implementation, duplicated per-file). The `+` button defaults new events to `SELECTED_KEY` (whichever day is currently open). See calendar.html's "Manual event create/edit" writeup for the full mechanism — it's identical here.

**Layout constants:**
```javascript
PX_HR = 80    // pixels per hour
DAY_START = 7  // 7am
DAY_END = 21   // 9pm, extends later if a bot event runs past 9pm
LABEL_W = 52   // width of hour label column
GAP = 12       // gap between labels and events
```

**Overlap prevention:** Sequential layout — each card's `top = max(naturalTime, prevCardBottom + 4px)`. Height estimates: XS=36, SM=72, full=max(ht,106).

**Date from URL:** Reads `?date=YYYY-MM-DD` param via `URLSearchParams` (parsed at module level outside React, not inside component — important, see tech notes). `TODAY_KEY` is computed from the real device clock (`todayKey()`), not a fixed date. Any other `?date=` looks itself up in `EVENTS_BY_DATE` (empty by default — see below) merged with that day's bot events, rendering a `SummaryRow` list instead of the hour grid, or `EmptyDay` if nothing exists for that date. Bot-created summary entries carry a real `id`/`start`/`end` (not just `{type,title}`) so they're tappable through to `action.html` same as a timeline `Bubble` — plain hardcoded entries (there are none by default) would stay inert.

**Chronological ordering + timestamps on the day-detail view (session 8):** `DAY_SUMMARY` (the non-today `SummaryRow` list) was built by simple `.concat()` with no sort at all, so a day with several bot-added events could list them in add-order rather than time order. Now sorted by `start` the same way `ALL_EVENTS` already was for today (`toMin(a.start || '00:00') - toMin(b.start || '00:00')`). `SummaryRow` also gained a time-range label (reusing the existing `timeRange()` helper the hour-grid `Bubble` already used), rendered between the title and the "✦ BOT" tag, guarded on `ev.start && ev.end` so it's a no-op for any hypothetical entry without times. Verified live: seeded three out-of-order bot events for a future day (6pm, 10am, 7am) and confirmed the list rendered `Gym 7–8 am` / `Team Sync 10–10:30 am` / `Birthday Party 6–8 pm` top to bottom.

**`SummaryRow` gained an edit pencil + a BOT-tag fix (session 9):** same manual create/edit feature as calendar.html — `SummaryRow` now renders a **✎** at the end of the row (any event with an `id`, `stopPropagation`'d so it doesn't also trigger the row's navigate-to-`action.html` click) that opens `EventModal` pre-filled with that event's data. While wiring this up, fixed a real mislabeling bug: the "✦ BOT" tag was previously shown for *any* clickable row (`!!ev.id`), which up to this point had only ever been true for actual bot-created events — but manually-created events also get an `id`, so without a fix every manually-added event would have incorrectly displayed "✦ BOT". Fixed by additionally requiring `ev.source !== 'manual'`. Verified live: a bot-style event (no `source` field) and a manually-added one on the same day — only the bot one shows the tag.

**Event data (session 5 — blank slate):** `EVENTS = []` and `EVENTS_BY_DATE = {}` — Benny has no seeded schedule. Everything that shows up here comes from `localStorage['cal_bot_events']`. The greeting subtitle and AI summary card are conditional on whether `ALL_EVENTS.length > 0`, so an empty day reads as "blank slate, ask the assistant" rather than showing fabricated content.

**Auto-scroll on open (fixed session 7):** reported bug — "when I create events for today they don't appear on the schedule." The data was always there (confirmed correct in every case tested); the timeline's mount-time auto-scroll just always scrolled to the *current clock time*, regardless of where events actually were. A quick call added for 4pm while it's 11am, for example, scrolled the page to show ~11am and left the event ~600px further down, off-screen with nothing hinting it existed there — reads exactly like "the event didn't get added." Fixed by scrolling to whatever's happening now *or next* instead (`ALL_EVENTS.find(ev => toMin(ev.end) > nowMin)`, falling back to the literal current-time position only if nothing's left today) — a newly-added event later today is now guaranteed to be the first thing visible without scrolling.

**Chronological ordering + timestamps (session 8):** reported request — day-cell events had no guaranteed order (bot events land in `cal_bot_events` in whatever order they were added/parsed, not necessarily time order) and showed no time at all, just a dot + title. Fixed by (1) carrying `start`/`end` through into `EVENTS_BY_DATE_MERGED`'s per-event objects (previously only `{type, title}` — start/end were dropped at merge time), (2) sorting each date's array by `start` right after the merge (`toMin(a.start || '00:00') - toMin(b.start || '00:00')`, module-level, before `App` even renders — this also means the "+N overflow" count reflects the *latest* events getting cut, not an arbitrary subset), and (3) a new compact `fmtDot()` helper (`9a`, `9:30a`, `2p` — no space, minutes only shown when non-zero) rendered before the title in each dot row, sized to fit the narrow day-cell width. **Manual event create/edit (session 9 — new feature):** reported request — add a way to manually create events (with action items) and edit existing ones, from both the Month view and the Today/day-detail view. Design:
- `EventModal` — a shared component (duplicated per-file, same pattern as `Nav`/`SettingsGear`) rendered as a centered overlay (backdrop click or `×` closes it, matching the click-outside-to-close pattern `action.html`'s `WeekModal` already used). Fields: Title, Date, Start/End time, Category (the same 6-type dropdown), Notes (optional, maps to `ev.sub`), and Action items (optional, one per line → `tasks[]`). Save is disabled until title/date/start/end are filled and `start < end`.
- `saveManualEvent(form, existingId)` — writes directly to the same `localStorage['cal_bot_events']` / `localStorage['cal_action_bot_tasks']` keys `bot.html` already uses, so every page's existing merge/render logic picks a manually-created (or manually-edited) event up with zero special-casing. `existingId` omitted → new event, `id: 'manual_' + Date.now() + '_0'`; passed → in-place update (find by id in the array, replace). Task ids follow the exact same `'bt_' + eventId + '_' + index` scheme `bot.html`'s `saveEventTasksToActionPage` uses, so `action.html`'s `tasksFor()`/checked-state lookups work identically for a manually-created event as for a bot-created one — **editing an event's action-item list also works for bot-created events**, not just manual ones, since it's the same underlying storage.
- Manual events get `type`-derived `emoji`/`tag` from the exact same `TYPE_EMOJI` map `bot.html` uses internally (`{ work: '🗓️', personal: '☀️', social: '☕', travel: '🚗', free: '🌿', health: '🏋️' }`), so a manually-added event looks identical in style to a bot-added one.
- `source: 'manual'` is set on every save (including when editing a previously bot-created event — editing it now marks it manual going forward, which is treated as correct: the content is now user-managed). This flag's only consumer is `index.html`'s `SummaryRow`, which hides the "✦ BOT" tag when `ev.source === 'manual'` (previously that tag showed for *any* event with an `id`, which would have mislabeled manual events as bot-created — fixed as part of this work, see index.html section).
- **Edit entry point:** a small hover-revealed **✎** pencil, per user's explicit choice, rendered directly on the event card/row itself (`DayCell`'s dot rows here; `Bubble`/`SummaryRow` on index.html) — not routed through `action.html`. Clicking it calls `e.stopPropagation()` then opens `EventModal` pre-filled with that event's current data (including its action items, read live from `cal_action_bot_tasks`).
- **Data refresh after save:** `EVENTS_BY_DATE_MERGED` (and index.html's `ALL_EVENTS`/`DAY_SUMMARY`) are computed once at module load, outside React state — same architectural pattern as everywhere else in this app (see "Data Architecture" below). `onSaved` calls `window.location.reload()` rather than trying to patch React state, consistent with that existing tradeoff.
- A real bug was caught and fixed during verification: `DayCell`'s merged event objects never carried a `date` field (only `id/type/title/start/end/sub/tag/emoji/source`), so opening the edit modal from the Month view left the Date field blank — confirmed live via a DOM inspection showing `date: ""` on the pre-filled form, fixed by adding `date: key` to the merge in `EVENTS_BY_DATE_MERGED`'s `forEach`, re-verified the edit modal then pre-fills the correct date.
- Verified live end-to-end: created "Dentist Appointment" via the `+` button (title/date/start/end/category/notes/2 action items), confirmed it landed correctly in `cal_bot_events` and `cal_action_bot_tasks` with matching ids; edited it via the ✎ pencil (changed the title), confirmed the *same* `id` was updated in place (no duplicate created) and the new title rendered on the grid; separately seeded a bot-style event (no `source` field) alongside a manually-added one on the same day and confirmed the "✦ BOT" tag shows only on the bot one.

### bot.html — AI Assistant

**URL:** `http://localhost:5173/bot.html`

**Purpose:** Full-screen chat interface powered by Claude. Persistent history via localStorage.

**Key components:**
- `Nav` — shared nav bar, active: `'bot'`.
- `renderText(text)` — custom text renderer. Parses bot response text line-by-line:
  - Lines starting with `•` → purple bullet
  - Lines with 2+ leading spaces → indented item (lighter color, tabular nums)
  - ALL-CAPS lines (letters only, no lowercase) → small purple section header
  - Empty lines → 5px spacer
  - Everything else → normal text
- `Message` — chat bubble. User: right-aligned purple gradient pill. Bot: left-aligned frosted glass, avatar is `<RobotIcon />` (idle state).
- `BotStatus` (renamed from `TypingDots`, session 2) — bouncing-dot bubble shown while `loading` is true, now with a state-changing avatar instead of the old ❆ emoji: `<BrainIcon />` for the first ~900ms ("thinking"), then `<CalendarFillIcon />` (animated — day cells light up in sequence) for however much longer the response takes ("scheduling"). All three (`RobotIcon`, `BrainIcon`, `CalendarFillIcon`) are hand-authored line-art SVGs, no emoji.
- `ActionBtn` — action suggestion buttons that appear under some demo responses / the "Save to action page", "Add event" (single event), and "Create plan" (multi-day plan) buttons (labels split in session 6 — see "Bot → Schedule Write-back"). One-shot (disabled after press, checkmark added), state persisted on the message object (`msg.done[label]`).
- `QuickOptionBtn` (session 5 as `TimeOptionBtn`, generalized + renamed session 6) — mutually-exclusive pill buttons for a "which of these works for you?" prompt — originally just time windows, now any small set of discrete choices (see "Proposing Quick-Pick Options" below). Picking one disables the others and shows a checkmark on the chosen one; the pick is persisted on the message (`msg.pickedOption`) so a reload can't un-pick it.
- `Suggestions` — 4 quick-prompt chips shown on first load only.
- `App` — manages message state, localStorage load/save, send logic, clear button.
- `MicButton` (session 12) — press-to-talk voice input. See "Voice input/output" below.
- `VoiceToggleButton` (session 12) — header speaker icon, mutes/unmutes the assistant reading replies aloud.

**Voice input/output (session 12 — new feature):** reported request — "talk to the assistant with voice, give it a british accent if possible." Implemented entirely client-side with the browser's native Web Speech API (no backend changes, no new dependency):
- **Input (speech-to-text):** `MicButton`, using `SpeechRecognition`/`webkitSpeechRecognition` (`lang: 'en-GB'`, `interimResults: true`, `continuous: false`). Tapping it starts listening (button turns red/pulsing); interim results stream live into the text input so it's visibly listening, and the final result auto-sends via `send(transcript)` — same one-shot flow as a real voice assistant, not a two-step "transcribe then manually hit send." Firefox has no `SpeechRecognition` implementation at all; `MicButton` feature-detects (`getSpeechRecognitionCtor()`) and renders nothing there rather than showing a control that can't work.
- **Output (text-to-speech, British accent):** `speakText(text)`, using `SpeechSynthesisUtterance` + `pickBritishVoice()`, which filters `speechSynthesis.getVoices()` for `lang === 'en-GB'` and prefers a named voice (`Daniel`/`Arthur`/`Google UK` — real synthesized voices, as opposed to a generic unnamed entry) when more than one is installed. Falls back to just `lang: 'en-GB'` on the utterance with no explicit `voice` if the browser has none installed at all, so speech still works (in whatever accent is available) rather than silently doing nothing. `cleanForSpeech()` strips `•` bullets and collapses blank-line paragraph breaks into ". " (with a follow-up regex to avoid a doubled ".." when the preceding sentence already ended in its own punctuation) before handing text to the utterance, so it reads naturally instead of speaking literal bullet characters or going silent on blank lines.
- Every new assistant reply is spoken automatically in `send()` (`if (voiceEnabled) speakText(result.text)`) — gated by `voiceEnabled` state (`loadVoiceEnabled()`/`saveVoiceEnabled()`, `localStorage['cal_bot_voice_enabled']`, **defaults to on**, toggled via the header's `VoiceToggleButton`, a `SpeakerIcon` that renders crossed-out when muted). `speechSynthesis.cancel()` is called both when a new message is sent (so a reply mid-playback doesn't talk over the next one) and when the mic starts listening (so the assistant doesn't talk over the user).
- Voice list warm-up: `speechSynthesis.getVoices()` returns `[]` in Chrome until the async `voiceschanged` event has fired once after page load — a bare `speechSynthesis.getVoices()` call plus a no-op `onvoiceschanged` handler at module load nudges the browser to populate the list early, so `pickBritishVoice()` isn't racing an empty list on the very first reply.
- **`MicIcon`/`SpeakerIcon`** — hand-drawn line-art SVGs (`currentColor`-based, so they inherit each button's idle/active tint automatically), same "no emoji" approach as the existing `RobotIcon`/`BrainIcon`/`CalendarFillIcon` set.
- Verified live: confirmed "Daniel" (a real `en-GB` voice) is installed in the preview browser and gets selected; patched `speechSynthesis.speak` to intercept and inspect the actual utterance sent for a real chat reply — correct voice (`Daniel`), correct `lang` (`en-GB`), correctly cleaned text (no `•`, no double periods after the fix). Clicking the mic button correctly triggers the browser's real microphone permission prompt (confirmed via the sandboxed preview pane's own mic-blocked notice — expected in that environment, not an app bug; a real browser tab would show the standard grant/deny prompt and proceed normally). Confirmed the mute toggle persists across reload and that muting suppresses `speakText` entirely.
- **Known limitation:** no voice control over feature *content* (add/remove events, quick-pick buttons, etc.) — voice only drives the chat's text in/out; picking a `QuickOptionBtn` or pressing an `ActionBtn` still requires a tap. Also Chrome-family only for input (`SpeechRecognition` — Safari has it too via webkit prefix, Firefox does not); output (`speechSynthesis`) has much broader support and works even where input doesn't, so a Firefox user would still hear replies spoken but have no mic button.

**Fixed a real cancel()/speak() race delaying every voice reply (session 13):** reported bug — "the voice always plays way after the message." Root cause, found by measurement rather than guessed at: `speakText()` called `speechSynthesis.cancel()` unconditionally on *every* call, immediately followed by `speechSynthesis.speak()` in the same synchronous tick — a well-documented Chrome bug where `speak()` called right after `cancel()` doesn't reliably start, sometimes silently stalling for several seconds before audio begins instead of the two being sequenced properly. Since `cancel()` ran before every single reply (not just when actually interrupting something), this was hitting the bug on effectively every turn, which lines up exactly with "always." Diagnosed by patching `window.fetch` and `speechSynthesis.speak` to log real timestamps (when the API response landed vs. when `speak()` was actually called vs. when audio actually started, via the utterance's own `start`/`error` events) rather than guessing from symptoms. Fixed by only calling `cancel()` when something is actually still playing (`speechSynthesis.speaking || speechSynthesis.pending`) — skipped entirely otherwise, which is the common case (by the time a ~1.5–2s API response lands, the previous reply has almost always already finished speaking) — and when a cancel genuinely is needed, adding a short `setTimeout` (150ms) before the next `speak()` so the cancel has time to actually land first, the standard workaround for this specific bug. Verified live: intercepted real timestamps across several genuine chat turns and confirmed the common no-interruption path now calls `speak()` within single-digit milliseconds of the reply arriving and audio starts within ~130ms — both fast and consistent, no multi-second gap. Note on verification limits: this preview environment's browser tab never reports as visible/focused (`document.visibilityState` stays `'hidden'` even after explicitly fronting the tab), which throttles background-tab timers in Chrome and made the *interrupt-mid-speech* path's exact timing impossible to measure cleanly here — confirmed the throttling was the confound (not the fix), but the 150ms delay's real-world reliability in a focused user tab rests on this being the standard documented mitigation for the underlying bug, not a live-measured number for that specific path.

**Deterministic time-conflict detection (session 13):** reported bug — "the bot only sometimes recognizes when times overlap for events. it ALWAYS needs to notice." Root cause: the system prompt never told Claude to check for schedule conflicts at all, so whether a reply happened to mention an overlap was purely up to the model's own unprompted judgment on any given turn — the same class of unreliability already documented for `QUICK_OPTIONS` and `REMOVE_EVENT` title-matching (see Open Issues). Since "always" was the explicit requirement and prompt wording alone tops out well short of that (per this file's own `QUICK_OPTIONS` history), fixed with real code instead of a stronger prompt:
- `findConflicts(newEvents, removalIds)` — checks every event `parseAddEvents` just proposed against (a) Benny's actual current schedule (`loadBotEvents()`, minus anything this same response is also removing via `REMOVE_EVENT` — a reschedule isn't a conflict with its own old slot) and (b) every other new event earlier in the same batch (in case Claude proposes two overlapping events in one response). Same-day, `toMin()`-based range overlap check (`rangesOverlap`), same pattern index.html/calendar.html/action.html already use for their own time math.
- Called inside `callClaude()` right after `resolveRemovals`, attached to the returned result as `conflicts`.
- New small helpers added alongside: `toMin`, `rangesOverlap`, `fmtT12` (bot.html previously had no time-formatting helper of its own — the other three pages each have their own copy of this same idea).
- Verified live: unit-tested `findConflicts` directly in the running page (seeded an existing "Team Sync" 10–10:30am event, checked a proposed "Dentist Appointment" 10:15–11am against it — correctly flagged; checked an unrelated 2pm event against the same schedule — correctly not flagged).

**Upgraded to an AI-judged resolution suggestion, not just a flat notice (session 13, same-day follow-up):** reported request — "instead of just saying time conflict have it judge which one is more important and ask if they'd like to move one of the things around," with the example phrasing "you were supposed to go to the gym at the same time as this meeting, want to go a little earlier to make both work." The original fix above (a static red `ConflictWarning` banner) satisfied "always notices" but not "judges and suggests" — banners can't reason about which event matters more or propose a specific fix, that's inherently a job for the model, not code. Replaced it with an automatic follow-up conversation turn:
- `buildConflictNudge(conflicts)` — builds a synthetic instruction (not from Benny, framed as an app-detected note) listing the exact conflicting event(s)/times/dates, asking Claude to judge which one seems harder to move (a meeting or something involving other people vs. a personal workout/errand/free block) and propose ONE practical fix — almost always shifting the more flexible one — as one short natural sentence ending in a `QUICK_OPTIONS` line with concrete new-time choices plus a "Keep both as scheduled" fallback. Explicitly told not to emit `ADD_EVENT`/`REMOVE_EVENT` itself — just propose; the actual change only happens once Benny picks an option, same as every other `QUICK_OPTIONS` flow in this file.
- `judgeConflict(conflicts, historySoFar)` — fires this as a second, separate `/api/chat` call (appending the synthetic nudge to the real conversation history so Claude has full context, but the nudge itself is never added to the visible `messages` state — only the reply is), parses the response through the same `parseAddEvents`/`parseRemoveEvents`/`parseQuickOptions` stripping the main pipeline uses (defensive, in case Claude ignores the "don't use those directives here" instruction anyway). On failure, falls back to a plain deterministic notice + a "Keep both as scheduled" option — this call can only ever fire after the main `callClaude()` call already succeeded (conflicts are only ever non-empty on that path — see below), so a live API is already known reachable; the fallback only guards this *second* call failing independently.
- `send()` now awaits both calls before updating state at all (kept `loading` true across both, rather than flashing "done" then popping in a second bubble) — pushes the normal reply, and, only if `result.conflicts.length`, a second assistant bubble with Claude's judgment call and real tappable resolution buttons. Removed the now-superseded `ConflictWarning` component and its render call entirely, per the request to replace the flat notice rather than keep both.
- Voice output speaks whichever bubble is most worth hearing — the conflict question when there is one, the normal reply otherwise.
- Verified live end-to-end with a real Claude conversation, not just unit tests: seeded an existing "Client Meeting" 2–3pm, asked live Claude to schedule a gym session 2:15–3pm. First attempt, Claude proactively asked before proposing anything (no conflict object generated that turn — the new mechanism only engages once an event is actually proposed, which is what happened next); told it to add the overlapping time anyway, and got exactly the target behavior: "Got it, adding it in!" + Add event button, immediately followed by a second bubble — *"Looks like the gym session overlaps your Client Meeting — since the meeting's harder to move, want to shift the gym to a different time today so both fit?"* — with real buttons `12:00-12:45pm` / `3:00-3:45pm` / `Keep both as scheduled`. Picked `3:00-3:45pm` and confirmed it flowed through the normal pipeline correctly: *"Done, adding your gym session at 3-3:45pm today!"* with a fresh non-conflicting Add event button, no new conflict raised.

**Removing from the schedule (session 7 — new):** Previously there was no way to remove a bot-created event at all; asking to cancel something had no effect beyond conversational acknowledgment. Now mirrors the `ADD_EVENT` pattern:
- `SYSTEM_PROMPT`'s "REMOVING FROM THE SCHEDULE" section teaches Claude it can cancel/delete things, but *only* by referencing an exact title from the live `CURRENT SCHEDULE` block (see above) — it's told explicitly not to guess or invent a directive for something it doesn't see listed there.
- Directive format, one line per event to remove: `REMOVE_EVENT: <exact title> | <YYYY-MM-DD>`, or `<exact title> | ALL` to cancel every occurrence of a title at once (e.g. scrapping an entire multi-day plan in one shot instead of day-by-day).
- `REMOVE_EVENT_RE` / `parseRemoveEvents(text)` extracts every matching line the same way `parseAddEvents` does; `resolveRemovals(removals)` matches each `{title, date}` pair against `loadBotEvents()` (exact-then-substring title match, same approach as `matchEventByTitle`) and returns the actual matched event ids. This resolution happens **inside `callClaude()`, at response time** — not later when the button is clicked — so the confirm button's count is accurate and immune to the schedule changing between response and click.
- The confirm button reads **"Remove event"** for a single match, **"Remove N events"** for multiple (e.g. cancelling a whole plan); clicking calls `removeEventsFromSchedule(ids)`, which deletes those ids from `cal_bot_events` *and* deletes any of their tasks from `cal_action_bot_tasks` (matched by `eventId`) — no orphaned checklist items left behind for a deleted event.
- Verified end-to-end: added a single "Call with Sarah" + "Dentist Appointment," asked to cancel just the call → got a "Remove event" button, clicked it, confirmed only the call was gone and the dentist appointment survived; then added a 5-day daily piano-practice plan and asked to cancel "the whole piano practice plan" → got "Remove 5 events" (model correctly emitted `... | ALL`), clicked it, confirmed all 5 were gone and the unrelated dentist appointment was untouched.

**Proposing quick-pick options (session 5 as time-only `TIME_OPTIONS`, generalized to `QUICK_OPTIONS` in session 6):** Whenever Benny would otherwise get an open-ended question that actually has a small set of sensible answers — not just "what time works" but "how long should each session be" (e.g. "20 or 30 minutes?"), "how many days a week," "how long should this plan run" — the system prompt requires the reply to end with a `QUICK_OPTIONS: <choice>; <choice>; <choice>` directive instead of writing the choices as prose bullets or burying them inline in the question. `parseQuickOptions()` (renamed from `parseTimeOptions`) strips it and the app renders real tappable buttons (`QuickOptionBtn`) instead. Investigated the "is memory broken" question first by intercepting real `/api/chat` request bodies mid-conversation — confirmed the full message history (all prior turns, byte-for-byte) is sent correctly on every single request, so this isn't a history/context-plumbing bug in the app; it's the model's own turn-to-turn reliability, worsened specifically on turns where it skips `QUICK_OPTIONS` and asks an open question instead — a free-text reply to an open question has less to anchor to than a button label does. ## Bot → Schedule Write-back

The bot can add events to the schedule directly — not just view it — including an entire multi-day plan (e.g. daily training sessions for a month) in one response, not just a single event at a time.

**Directive format (`bot.html`):**
- `SYSTEM_PROMPT`'s "ADDING TO THE SCHEDULE" section teaches Claude to emit one line **per event**, each carrying its own date and an optional inline task list:
  `ADD_EVENT: <Title> | <YYYY-MM-DD> | <start HH:MM>-<end HH:MM> | <type> | <task1; task2; task3>`
  (`type` is one of the 6 categories; the trailing task field is semicolon-separated and optional but the `|` is always present). For anything spanning more than one day, the prompt instructs Claude to output one `ADD_EVENT` line per day/session — using the real current date (`TODAY_KEY`, computed at load time) as its anchor — and to use judgment on rest/off days rather than forcing an identical block onto every single day.
- `ADD_EVENT_RE` (global + multiline) / `parseAddEvents(text)` extracts **every** matching line via `matchAll`, builds an array of event objects (`{ id: 'bot_'+timestamp+'_'+index, type, emoji, title, sub: 'Added by assistant', date, start, end, tag, tasks: [...] }`), and returns the *display* text with all directive lines stripped out — Benny never sees the raw lines, only a natural confirmation plus a single button: **"Add event"** for a single one-time event, **"Create plan"** for a multi-event/multi-day plan (relabeled in session 6 — was "Add to schedule" / "Add N to schedule"). A trailing partial `ADD_EVENT:` line (from a response that got cut off — see session 5's `max_tokens` fix) is also stripped defensively even when it didn't fully match.
- **Real multi-event parsing bug found + fixed in session 7:** asking for two events in one message (e.g. "add a call today AND a dentist appointment tomorrow") silently dropped the second one — its entire `ADD_EVENT:` line got swallowed as literal text into the *first* event's `tasks` array. Root cause: the regex used `\s*` (which matches `\n`, not just spaces/tabs) directly before the final `(.*)$` tasks-field capture; when an event's tasks field is empty, that trailing `\s*` would greedily consume the newline separating it from the *next* `ADD_EVENT:` line, and `(.*)$` then kept matching into that next line since `$` in multiline mode just needs *a* line ending, not the original one. Fixed by rewriting `ADD_EVENT_RE` (and `REMOVE_EVENT_RE`, same construction, same risk) to use `[ \t]*` — horizontal whitespace only — around every field separator, so no field's match can ever cross a line boundary regardless of which fields are empty. Also added `normalizeDirectiveLines(text, name)`, a defensive second layer that force-inserts a newline before any mid-string occurrence of a directive name not already at a line start (covers the *other* theoretical failure mode: the model running two directives together with no newline at all, which didn't turn out to be what actually happened here, but costs nothing to guard against). Verified with the exact repro phrase (call + dentist appointment) — both events now parse and save correctly, confirmed via a raw-`fetch`-response intercept to compare before/after against the actual Claude output, not just guessed at.

## Critical Technical Notes

### ⚠️ No Template Literals Inside JSX
Babel standalone (CDN version) cannot reliably parse template literals inside JSX expressions or attribute values. This causes a silent parse failure — the entire page goes blank.

**Rule:** Template literals (backticks) are ONLY allowed in plain JavaScript functions, not inside any JSX. Use string concatenation instead.

```javascript
// ✅ Safe — inside a plain JS function
function toKey(y, m, d) {
  return `${y}-${m}-${d}`;
}

// ✅ Safe — in JSX, use string concatenation
border: '1px solid ' + c.bd,
window.location.href = 'index.html?date=' + dateKey;

// ❌ Will crash the page
border: `1px solid ${c.bd}`,
onClick={() => { window.location.href = `index.html?date=${key}`; }}
```

### URLSearchParams Must Be Outside React Components
If `new URLSearchParams(window.location.search)` is called inside a React function component body, Babel standalone sometimes fails to compile the file. Always parse URL params at module level (outside any function):

```javascript
// ✅ At module level, outside App()
const _dp = (function() {
  try { return new URLSearchParams(window.location.search).get('date'); } catch(e) { return null; }
})();
const DISPLAY_DATE = _dp ? new Date(_dp + 'T12:00:00').toLocaleDateString(...) : new Date().toLocaleDateString(...);
```

### Nav Component Is Duplicated
The `Nav` component (and now `SettingsGear`, and the theme `:root`/`[data-theme]` CSS block) is copy-pasted into all five pages. If you modify the nav, the gear icon, or a theme token, update it in all five files. A shared JS/CSS include would be cleaner but would require a build step.

### Dev Server Launch Config Was Stale (fixed)
Both `.claude/launch.json` (project) and the global `~/.claude/launch.json` had a stale `cwd`/`--directory` pointing at a nonexistent `/Users/Zack/calendar-prototype` (missing the `Desktop` segment), and the global one ran plain `python3 -m http.server` instead of `server.py` — losing the `/api/chat` proxy. Both now point at `/Users/Zack/Desktop/calendar-prototype` and run `python3 server.py`. The global config (`~/.claude/launch.json`) is the one actually used when the Claude session's cwd is `~` rather than the project dir — keep both in sync if either changes.
